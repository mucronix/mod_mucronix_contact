Notes on extra fields

The Extra Fields tab is the one place in the module where markup is written by hand. Below: a ready-made example for every field type, a set for a typical form, and everything the module refuses, with the reasons.

How it works

  • Fields are written into Field Description in the Joomla form format, one <field> element per field. There is no need to wrap them in <form> or <fieldset> — write the fields one after another.
  • On the page they follow the module's own fields, in front of the captcha, in the order they are written. They reach the mail and Telegram in that same order.
  • Every field needs three things: a name, a type and a label. The name is in Latin letters and the visitor never sees it; the label is in the language of the site.
  • required="true" makes a field mandatory.
  • After saving the module, open the page with the form while still logged in to the administrator. If anything was refused, a notice with the reason appears above the form. Only people who can manage modules see it; visitors get the form as usual. What each notice means is in section 6.

What the server checks and what only the browser does. On their own, pattern, maxlength, min and max work in the browser only: a hint to the visitor, not a safeguard. The check on the server is switched on by validate — the examples below carry it where it is needed.

1. The eleven types

Each example can be pasted as it stands. Put your own label and options in; rename if you like.

text — one line

<field name="company" type="text" label="Company" maxlength="100" />

textarea — several lines

<field name="address" type="textarea" label="Delivery address" rows="3" />

email — one more address

<field name="email_extra" type="email" label="Second email" validate="email" />

Without validate="email" only the browser checks the address. The main Email field is the module's own and does not have to be added here.

tel — a phone number

<field name="phone" type="tel" label="Phone" inputmode="tel" validate="tel" />

validate="tel" takes 7 to 15 digits; a plus, spaces, dots, hyphens and brackets between them are allowed. inputmode="tel" brings up the numeric keypad on a phone: Joomla prints the field itself as an ordinary text box.

url — a web address

<field name="website" type="url" label="Your website" hint="https://" validate="url" />

An address is accepted only with https:// or http:// in front: a bare example.com is refused, which is why the hint in the box earns its place.

number — a number

<field name="guests" type="number" label="Number of guests" min="1" max="20" step="1" validate="number" />

With validate="number" the server keeps to min and max as well.

list — a drop-down

<field name="topic" type="list" label="Subject" validate="options">
    <option value="">— choose —</option>
    <option value="question">A question</option>
    <option value="order">An order</option>
    <option value="other">Something else</option>
</field>

The mail carries the wording of the option ("An order"), not its value (order). The first line with an empty value is what stops a mandatory list from being sent unchosen.

radio — one of several

<field name="reply_by" type="radio" label="How should we reply" default="mail" validate="options">
    <option value="mail">By email</option>
    <option value="call">By phone</option>
</field>

The options are not optional: without them the page shows a label with no control under it.

checkbox — a single tick box

<field name="callback" type="checkbox" label="Call me back" value="1" />

The mail says "Yes" or "No". A mandatory tick box is left out of the mail altogether: the form cannot be sent without it, so the answer is always the same.

checkboxes — several tick boxes

<field name="interests" type="checkboxes" label="What are you interested in">
    <option value="price">Prices</option>
    <option value="terms">Lead times</option>
    <option value="demo">A demonstration</option>
</field>

The mail lists the wordings of the ticked options, separated by commas.

calendar — a date

<field name="visit_date" type="calendar" label="Preferred date" />

The date arrives as 2026-10-15.

2. A ready-made set for a typical form

A phone number, a subject, a convenient time and a newsletter opt-in. Paste the whole thing and it works at once.

<field name="phone" type="tel" label="Phone" hint="+44 20 7946 0958"
    pattern="[0-9+\(\) \-]{7,20}" inputmode="tel" validate="tel" required="true" />

<field name="topic" type="list" label="Subject" required="true" validate="options">
    <option value="">— choose —</option>
    <option value="question">A question</option>
    <option value="order">An order</option>
    <option value="other">Something else</option>
</field>

<field name="call_time" type="radio" label="When is a good time to talk" default="any" validate="options">
    <option value="any">Any time</option>
    <option value="morning">Before noon</option>
    <option value="evening">After noon</option>
</field>

<field name="newsletter" type="checkbox" label="Send me your news" value="1" />
  • pattern on the phone stops letters right in the browser, before the server is asked. The brackets and the hyphen inside the square brackets carry a backslash on purpose: without it the browser silently drops the whole pattern and lets anything through.
  • The newsletter opt-in is an optional tick box, separate from the consent to data processing. The mail says "Yes" or "No", so you see who agreed. Make it mandatory and everybody is forced to agree, and the answer no longer appears in the mail.
  • Do not add the consent to data processing here: the module has its own, the Consent Checkbox setting on the Fields tab.

How to check: send the form with no phone and no subject — both fields should be marked, each with its own message. Then fill it in and send: the subject arrives in the mail as "An order", not as order.

3. Names that are taken

Eight names belong to the module itself, and a field carrying one of them is skipped:

name, email, message, attachment, consent, captcha, mcx_hp, mcx_module_id.

Case makes no difference: Email and CAPTCHA are taken just the same.

The reason: when Joomla meets a second field of the same name it does not add it, it puts it in place of the first — and says nothing. captcha is the worst case: an ordinary text box that is satisfied by any value would stand where the check was, and the form would go on believing itself protected. With mcx_hp the same happens to the trap for robots.

For a second address or a second message, call the field something else: email_extra, details. For a file, switch on the Attachment Field on the Fields tab.

Two extra fields of one name do not get along either: the first one stays.

4. Attributes the module takes off

The field itself stays and works; only the attribute goes, and a notice above the form says which one.

  • id — Joomla builds the identifier from the name by itself. Set by hand, it gets round the list of taken names: a field of any name with id="mcx_hp" pushes the trap for robots off the page, and the protection is gone without a sign.
  • layout, layoutIncludePath — swap the file that draws the field for a file named in a setting.
  • fieldset, formsource — move the field elsewhere on the page or pull in a form description from outside.
  • addfieldprefix, addformprefix, addruleprefix, addfilterprefix, addfieldpath, addformpath, addrulepath, addfilterpath — decide which code stands behind the word in type. With them the list of accepted types means nothing at all: the description still says text while somebody else's class does the work — and does it for every form built on the page after this one.

An ordinary form needs none of these attributes.

5. What a name may look like

A Latin letter first, then Latin letters, digits and the underscore: ^[a-zA-Z][a-zA-Z0-9_]*$.

Fine: phone, call_time, phone2. Not fine: call-time, call.time, 2phone, téléphone.

The hyphen and the dot are not banned out of strictness. Joomla makes the identifier of a field on the page out of its name, turning everything except letters, digits and the underscore into an underscore. call-time, call.time and call_time would all get the same identifier, and one of the three would be left on the page — silently.

6. Reading the notices

All of them appear above the form and begin with "Extra fields". None of them stops the form from being sent: a skipped field is simply not shown, and the rest work.

Extra fields: the description could not be read, so no field was added.
A mistake in the writing itself: a tag left open, a lost quotation mark, the slash missing from the closing />. The notice goes on to name the line and the reason — that line is the one to mend. Until it is, no field is added, the correct ones included.
Extra fields: the description holds no field element, so nothing was added.
The text can be read, but there is no field in it. Usually a misspelt field, or some text left where the description should be.
Extra fields: a field without a name was skipped.
Give the field a name.
Extra fields: the name … was refused and the field skipped.
The name holds something other than Latin letters, digits and underscores, or does not start with a letter. See section 5.
Extra fields: the name … belongs to the module and the field was skipped.
A name from the list in section 3. Call the field something else.
Extra fields: the name … is used more than once, only the first field was kept.
Two fields of one name. Rename the second.
Extra fields: the field … has no type and was skipped.
Give the field a type — one of the eleven in section 1.
Extra fields: the field … was skipped, the type … is not accepted here.
The type is not one of the eleven. Check the spelling — checkboxes, not checkbox-list — and look at section 7: the type may be refused on purpose.
Extra fields: the attribute … was removed from the field ….
The field works; only the attribute named was taken off. Remove it from the description and the notice goes away. See section 4.

The same reasons, in one line each, are written to the log administrator/logs/mod_mucronix_contact.php — every time the form is sent, for as long as the description stays unmended.

7. What will never be accepted

Joomla has far more than eleven field types. These seven are refused on purpose:

  • sql — runs the query written in its attribute and shows on the page what the database answered. The right to edit a module would turn into the right to read tables.
  • user — brings the administrator's user picker onto a public page.
  • file — opens a second upload that goes round the checks on the first. For a file there is the Attachment Field.
  • subform — builds fields inside a field; the checks on names, types and attributes do not reach them.
  • editor — pulls the administrator's editor onto a public page, buttons and all.
  • accessiblemedia — the same, with the image picker of the media manager.
  • hidden — puts a value into the message that the visitor neither typed nor saw.

A phone number, a list, a date, tick boxes — whatever a contact form needs, the eleven types cover. If a field from this list is the one thing missing, what is needed is a form builder, not this module.
